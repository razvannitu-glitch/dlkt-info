# DLKT audience foundation (staged, not activated)

First-party, opt-in measurement design. The unit is a consenting browser, not a verified person or account. It is intentionally isolated from public news, account identities and payment records. This commit exposes no public endpoint, writes no cookies, makes no runtime database changes and enables no collection.

The token contract uses a purpose-bound HMAC and a random identifier with a fixed 90-day expiry. The browser digest, not the token, is stored. The SQL contract in scripts/audience-schema.sql is a staged schema for a separately reviewed analytics database boundary. It is not in the application's automatic migrations. All tables, including the revocation tombstone table, have RLS enabled, no anon/authenticated grants, and invoker functions with explicit service-role privileges. No exact IP, GPS, device fingerprint, URL, title, personal profile or account identifier is stored. Geography is approximate session-entry geography only; the collector must independently establish trusted ingress before using platform headers. Country/city cells below three distinct browsers are suppressed. Source is a coarse allowlisted group, not a referrer URL.

A session starts with a pageview and ends after 30 minutes without recorded activity; presence signals cannot start a new browser or resurrect an expired session. Presence updates are coalesced to at most one session-row update per minute; pageview IDs deduplicate retries and writes are capped at 30 accepted pageviews per browser per rolling minute. The snapshot reports unique measured browsers overlapping the selected range, session starts, pageviews, repeat browsers with at least two sessions overlapping that range, and browsers active within the last five minutes (not exact simultaneous people). Hourly/daily series show pageviews and session starts in UTC. All time means the retained 90-day window. These are consent-based counts, not a census of all visitors. Data coverage starts only after verified activation; an unavailable provider or uninitialized collector must not be shown as zero.

Before activation: review applicable privacy/ePrivacy rules and notices; implement explicit choice, withdrawal, strict same-origin checks, protected secret, ingress validation, request-size and global abuse controls, retention scheduling and monitoring, a separate least-privilege storage transport and operational cost tests. Review the schema and test in isolated integration; do not weaken existing production readiness attestation. Integrate the dashboard only after the actual source is validated. Category interactions and financial reporting require a separate minimized aggregate design. No sensitive category-level browser histories should be created.

Withdrawal deletes linked activity and retains only a pseudonymous digest tombstone for at most 90 days to reject in-flight or replayed tokens. Ingestion and withdrawal share a transaction lock. The browser gateway must still clear its token and stop sending events. Session activity is coalesced, so active counts and timeout boundaries are approximate by up to one minute. The database purge and withdrawal functions are available for integration tests; scheduling, browser consent UI, HTTP ingestion, dashboard adapter and live credentials are deliberately not implemented or activated in this foundation.
