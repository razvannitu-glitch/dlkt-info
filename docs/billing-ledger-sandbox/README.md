# Billing persistence laboratory (draft; not a deployment)
Tracks #65; stacked on reviewed PR #67 head `1498bbfa7c6e054ba1c6413fb75ca78fcbc1f93e`. Source pin, canonical source, production configuration and the editorial workstream are untouched. No live migration is authorized (see #68).

This disposable PostgreSQL candidate defines six private, sandbox-only tables: account and price catalog, immutable customer ownership and subscription identity, exclusive open checkout reservation, and deduplicated signed-notice identity. Explicit schema/table/column grants and RLS deny direct browser access. The runtime role is modeled on Supabase service_role (BYPASSRLS); production should evaluate a narrower dedicated server role. A customer tombstone is a provisional deletion/cancellation design, not a retention policy.

The ledger **does not** process Stripe transactions, close checkout slots, persist payment evidence, reconcile risk, or grant Premium. The checkout slot deliberately cannot be released by the runtime role in this increment; a verified transactional terminal-state operation and idempotent session creation must precede any use. A signed notice is not trusted payment evidence. Duplicate event IDs must not be treated as completed processing. Future event processing must include durable state, fenced leases, out-of-order handling, conflict detection and transactional reconciliation. No actual data, credentials, raw event bodies, URLs, emails or payment information are used.

The branch-only CI workflow runs setup, ledger and SQL assertions in a disposable PostgreSQL 17 service, with synthetic roles and IDs and read-only repository token. No production or Stripe credentials are available. It uses the official mutable postgres:17 image only for the disposable test; pin a verified image digest before a durable release pipeline. Successful local SQL assertions are not proof of Supabase integration, concurrent runtime requests, provider payment or application authorization. Real sandbox lifecycle, production ACL/RPC verification, retention/deletion, migration generation and rollback after a verified recovery path remain release gates. Do not merge this laboratory into main as a production migration.
