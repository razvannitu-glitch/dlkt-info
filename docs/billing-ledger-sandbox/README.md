# Billing persistence laboratory (draft; not a deployment)
Tracks #65; stacked on reviewed PR #67 head `1498bbfa7c6e054ba1c6413fb75ca78fcbc1f93e`. Source pin, canonical source, production configuration and the editorial workstream are untouched. No live migration is authorized (see #68).

This disposable PostgreSQL candidate defines six private, sandbox-only tables: account and price catalog, immutable customer ownership and subscription identity, exclusive open checkout reservation, and deduplicated signed-notice identity. Explicit schema/table/column grants and RLS deny direct browser access. The runtime role is modeled on Supabase service_role (BYPASSRLS); production should evaluate a narrower dedicated server role. A customer tombstone is a provisional deletion/cancellation design, not a retention policy.

The ledger **does not** process Stripe transactions, close checkout slots, persist payment evidence, reconcile risk, or grant Premium. The checkout slot deliberately cannot be released by the runtime role in this increment; a verified transactional terminal-state operation and idempotent session creation must precede any use. A signed notice is not trusted payment evidence. Duplicate event IDs must not be treated as completed processing. Future event processing must include durable state, fenced leases, out-of-order handling, conflict detection and transactional reconciliation. No actual data, credentials, raw event bodies, URLs, emails or payment information are used.

The branch-only CI workflow runs setup, ledger and SQL assertions in a disposable PostgreSQL 17 service, with synthetic roles and IDs and read-only repository token. No production or Stripe credentials are available. It uses the official mutable postgres:17 image only for the disposable test; pin a verified image digest before a durable release pipeline. Successful local SQL assertions are not proof of Supabase integration, concurrent runtime requests, provider payment or application authorization. Real sandbox lifecycle, production ACL/RPC verification, retention/deletion, migration generation and rollback after a verified recovery path remain release gates. Do not merge this laboratory into main as a production migration.

## Queue laboratory extension
`queue.sql` is a separate experimental extension, applied **only after** the baseline test in the disposable database. It replaces direct notice insertion with atomic intake, detects conflicting duplicate identity, and adds a private job table with bounded leases, monotonic per-event attempt fences, delayed retries, dead-lettering and machine-role separation. The three SECURITY DEFINER functions are needed to encapsulate permitted state transitions without granting callers direct job-table writes; the function owner is a dedicated NOLOGIN/NOBYPASSRLS role with narrow table ACLs, fixed search_path, no CREATE and no browser execution. The queue worker cannot ingest and the intake role cannot process. No user-context endpoint is exposed. Production role provisioning/connection strategy is not decided.

Thirty-second leases and retry delay, five attempts and a bounded 32-row expiry sweep are provisional lab parameters, not an approved operational SLA. A routed result means only successful routing, never a verified payment, final reconciliation or entitlement. Attempt fences protect one event, not ordering across multiple events for the same subscription. Before an actual billing worker can write business state, add per-subscription fencing and transactional authoritative provider reconciliation, error alerting and retention. Test fixture modifications to deadlines occur only as the disposable DB administrator. The workflow tests two independent sessions contending for the same event and lease; it does not test a real Stripe webhook endpoint.

## Subscription reconciliation laboratory extension
`reconcile.sql` adds per-subscription durable generations, a strictly increasing lease fence, atomic routing of directly addressed subscription notices, independent machine roles and a non-authorizing observation receipt. An older event arriving later invalidates the prior observation and requests a new read; provider event creation time is never treated as business-state order. A new generation cancels the previous lease, and expired or superseded generations/fences cannot commit. The account, owner, customer, item and price must match the existing immutable binding. The observation stores only a status, database timestamp, and generated constants funds_confirmed=false and risk_state=unknown. The database does not verify Stripe HTTPS itself. A real adapter must obtain fresh authenticated data after claiming the generation and compare every identity. No entitlement is derived from these receipts, including after owner deletion.

The earlier direct routed completion capability is revoked from the worker; a directly addressed subscription notice and its reconciliation request commit together. Invoice, Checkout, charge and dispute linkage is deliberately unsupported until the authenticated provider mapping is implemented. A missing/deleted binding cannot be routed; operational handling of orphaned jobs and financial cancellation obligations remains a release gate. Reconciliation uses a provisional 60-second lease, 30-second retry delay, five attempts per generation and bounded expiry sweep. The observation is not a substitute for paid invoice line coverage, funding or refund/dispute evidence. Out-of-order unmapped events, recurring refresh, runtime authentication, monitoring, real Stripe tests and secure account deletion/cancellation remain open. The SQL is tested only in disposable PostgreSQL 17, not applied to Supabase.

## Authenticated card-payment observation laboratory
The independent TypeScript module `payment-proof.ts` reuses the existing StripeReadClient for the verified sandbox account/catalog and bound subscription, then uses fixed HTTPS GET routes with restricted test credentials for an exact current-period invoice, its single subscription line, InvoicePayment allocation, PaymentIntent, captured Charge and complete empty refund/dispute/early-warning lists. It rejects ambiguous, multi-payment, external/manual, discount, credit, proration, noncard and nonempty tax cases. This intentionally conservative pilot is NOT an approved commercial policy or a complete fiscal/Stripe integration. No authorization follows from the result: fundsConfirmed=false and riskState=unknown are fixed; a snapshot cannot promise absence of later fraud or settlement failure. Test clock and provider responses are synthetic; the exact pinned version's real response shape must be verified against actual sandbox lifecycle before promotion. No real subscriptions existed at connector readback; no test customer/payment was created in this increment. No app secrets, account-wide settings, fiscal changes, provider writes or live calls. See official Stripe docs for [Invoice Payments](https://docs.stripe.com/api/invoice-payment), [Invoice line items](https://docs.stripe.com/api/invoice-line-item/object), [refunds](https://docs.stripe.com/api/refunds/list), [disputes](https://docs.stripe.com/api/disputes/list) and [early fraud warnings](https://docs.stripe.com/api/radar/early_fraud_warnings/list). Before production integrate the read path with per-subscription generation/fence, exact provider ID resolution, bounded overall deadline, fresh clock, recheck invalidation and real sandbox tests; consolidate the additional transport with the canonical read client. No migration or source pin modification.

## Checkout lifecycle laboratory
`checkout.sql` extends the disposable ledger with fixed-expiry reservations, immutable test-session attachment, verified terminal receipts and atomic subscription binding/reconciliation enqueue. A machine-only API role may reserve and attach; a separate recovery role may read/attach/finish but cannot initiate a purchase. The restricted nonlogin definer owns only functions, with fixed search_path, RLS policies and narrowly scoped table privileges. Direct service_role inserts into checkout and subscription bindings are revoked. One customer/intent lifetime in this first-purchase-only laboratory is an explicit conservative limitation; even expired sessions are not automatically replaced. No missing response, cancellation redirect or local timeout is a terminal provider observation. No hosted URL is persisted. Completion requires an independently authenticated exact provider observation; the SQL does not verify Stripe itself. A successful terminal receipt creates a pending reconciliation job, with funds_confirmed=false and risk_state=unknown; no grant. A conflicting session or subscription rolls back the whole terminal transaction. Deleted owner bindings are not returned; financial cancellation, orphan cleanup and coordinated auth deletion still require a release-grade workflow. Provisional fixed expiry 1h; no changes to canonical source, production DB, fiscal settings or Stripe. Tested only in disposable PostgreSQL with synthetic identities.

The TypeScript recovery path performs a read-only customer session list plus exact Checkout GET and full line verification. It never creates a replacement when a known session is absent. A verified complete session must resolve to exactly one bound catalog subscription and its exact item; a verified expired session must be unpaid with no associated subscription. A complete session is not proof of funds or risk. `checkout-lifecycle.ts` is the server orchestration contract with separate API and recovery persistence ports: it requires durable attachment before releasing a redirect URL, handles ambiguous provider failures by leaving the reservation intact, and returns only a terminal receipt from recovery. It does not implement the actual SQL transport or user-session authorization; the adapter must normalize SQL row names and BIGINT epoch fields, supply ownerId from authenticated server identity, and invoke the exact scoped functions. The caller must recheck session/account access at runtime. The first-purchase policy, no automatic replacement after expiry, test-only card/tax assumptions, lack of real provider delivery, and production recovery/fiscal gate remain unchanged.

## Synthetic entitlement gate laboratory
`entitlement.sql` adds a transactional account-wide invalidation epoch updated on first durable notice insert, a claim context tied to the reconciliation generation/fence/epoch, and a short-lived **synthetic_fixture** candidate receipt. The sandbox fixture writer is a separate NOLOGIN role, never granted to the actual reconciliation role or public API. Neither a captured-card observation (which still has fundsConfirmed=false/riskState=unknown), a paid Checkout receipt, nor a normal observed subscription can publish a positive fixture. The reader requires current owner, exact completed checkout/subscription binding, matching generation/fence/epoch, active observation, fresh paid-period candidate and no pending/leased/dead notices in the account. Any new notice invalidates before routing; duplicate receipt does not increment. Account-wide invalidation is deliberately overconservative until authenticated event-to-subscription mapping is complete; dead jobs block candidates until resolved. Five-minute maximum age and cancellation cutoff follow the existing draft policy. The fixtures are not payment evidence, real Premium grants or production migration. No role is provisioned in Supabase. Runtime session checks, real evidence publication, periodic refresh, per-subscription event mapping, provider action gates and actual Stripe acceptance remain required. Read-time checks do not make later external actions atomic; recheck before sensitive operations and commits.

The TypeScript fixture boundary applies the existing canonical policy to an exact persisted synthetic receipt and performs a second storage read after catalog validation. A missing or changed receipt, clock regression, expiry, wrong owner/account or unverified catalog denies eligibility. Its positive result is deliberately `sandbox_eligible`, NOT `premium`, and requires the explicit `synthetic_fixture_only` gate. It cannot be wired into actual provider access as a positive authorization. The real card proof reader remains non-authorizing. No runtime DB adapter, live payment evidence or authenticated user route has been connected.
